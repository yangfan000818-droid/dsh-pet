# X27 群架：联机各自为战（设计与任务书）

2026-10-30。分支 `x27-brawl`。来自用户需求：能不能做打群架的，**各自为战**；人数上限 **5**；五只（含自家宠物）**围成一圈**；攻击要**打到具体那一只身上**，观感尽量贴近 1v1。

本文既是设计也是任务书。每个任务写清现状、改法、测试和验收；主会话负责核验。和现有文档冲突时以本文为准。

## 0. 范围

**目标**：局域网里 2–5 只桌宠进同一场混战，各打各的，最后站着的赢。五只绕成一圈同屏演出，每一招的飞行物、受击、闪避、血条都落在具体的目标身上。

| 做                                                               | 不做                                   |
| ---------------------------------------------------------------- | -------------------------------------- |
| 2–5 人混战内核（N 方事件、选目标、同时刻串行）                   | 组队（各自为战，没有阵营）             |
| 本地环形摆位与多窗口（本机宠物 + N-1 个对手窗口）                | 观战、转播、托管                       |
| 联机组局、名帖与 nonce、出手广播、掉线/认输退场、房主移交        | 打到一半中途加入                       |
| 手动出招 + 手动选目标                                            | 跨平台协议兼容（版本不同直接进不去）   |
| 混战平衡模拟                                                     | 改 1v1 的切磋、历练、秘境、心魔、渡劫  |

**硬边界**：

- 1v1 全链路一行不动：`fight()`、`BattleEvent`、`timeline()`、`ShowSides`、`startLiveClient/Server` 保持原样。群架走新文件、新事件类型、新演出入口，避免把 `battle.test.ts` 那 2826 行按二元组写的用例全部推翻。
- 规则语义复用 `Fighter` / `Side`：法宝、招式、泡泡、魂影、蓄力、领域、瞬影、控制、假死遁的口径照旧，只是「对方」变成「选中的目标」。
- 联网只传名帖、nonce、每手选择与退场信号；结算和收益各算各的，不传结算结果。

## 1. 现状盘点

## 2. 内核：N 方混战

### 2.1 文件与类型

新增 `src/app/brawl.ts`，不碰 `battle.ts` 的既有导出。规则常量（伤害、控制、护体、蓄力……）从 `battle.ts` 导入，不复制数值。

```ts
export interface BrawlFighter extends Fighter {
  /** 本场编号 0..N-1；0 号是房主 / 本机发起方 */
  id: number;
}

export type BrawlAction = Action & { target: number };

export type BrawlEvent =
  | { actor: number; kind: 'start'; hp: number[] }
  | { actor: number; kind: 'decide'; action: BrawlAction; hp: number[] }
  | { actor: number; kind: 'hit'; target: number; damage: number; crit: boolean; blocked: boolean; hp: number[] }
  | { actor: number; kind: 'dodge'; target: number; hp: number[] }
  | { actor: number; kind: 'miss'; target: number; hp: number[] }
  | { actor: number; kind: 'ko'; target: number; hp: number[] }
  | { actor: number; kind: 'forfeit'; target: number; hp: number[] }
  | { actor: number; kind: 'end'; winner: number | null; ranking: number[]; hp: number[] };
// 其余事件（combo / bubble / mirror / play-dead / skill / skip …）照 BattleEvent 的字段，
// 把 actor 换成编号、补 target、hp 换成数组。
```

`hp` 是**按编号排列的全场气血快照**，每只都带，演出要据此同步 N 条血条。

### 2.2 出手顺序

- 沿用 `Side.next` 的遁速时间轴：出手间隔 `100 / (遁速 + 10)` 秒，开局随机延迟 ×0.8–1.2。
- 每轮取 `next` 最小且还活着的一方；**同一时刻（差值 < 1e-6）按编号从小到大串行**，不并行结算。这样事件序列永远确定，各家重算一致。
- 被控跳过、蓄力自动释放、鬼敲门补击、前有古人补击都照 1v1 的语义，只把「对方」换成已选目标。
- 一场上限沿用 `MAX_ACTIONS = 30`；到点按剩余气血比例排序，比例相同比击杀数，再相同比编号。

### 2.3 目标选择

- `BrawlAction.target` 必须是**活着且不是自己**的编号；引擎校验，非法动作直接报错（联机里由房主拒收）。
- 直接伤害、控制、指定对方的效果（墨汁、鬼画、吃苦吃亏、万我大手印、鬼手……）都走目标；自身增益（凭空生花、逆流护身印、深渊领域、瞬影、聚气）不需要目标。
- **AI 挑目标**：先筛活人，再按「残血优先 → 刚出过手优先 → 编号」打分，带一点随机；具体权重进 B5 调。
- **随机数纪律**：每次「选目标」固定消耗一次决策随机数（即使只有两个活人），手动与自动都抽。这样换目标不会挪动后续结算序列，回放和联机重算才对得上。

### 2.4 淘汰与胜负

- 气血归零（假死遁救回的不算）→ `ko` 事件，该编号退出排序、不能再被选为目标。
- 剩 1 人 → 结束，`end.winner` 是它。
- 所有人同时归零（同一下多段打死最后两人）→ `winner: null`，按 §2.2 的规则排 `ranking`。
- 认输 → `forfeit` 事件，等同淘汰，继续打。

### 2.5 数值口径

- 群架默认走**切磋节奏**：伤害 ×0.65、单发最多打掉目标上限 30%（`FightOptions` 那套），避免 5 人局一手秒人。
- 主动技额度：每人每场 3 次（沿用 `SPAR_ACTIVE_LIMIT`），招牌必中招照旧必中，普通主动技恢复闪避判定。
- **AI 目标分散**：主目标只在「剩余气血比例最低的一档（差 12% 以内）」里随机挑，不按编号集火。B0 模拟发现确定性选目标会让编号最大的稳定获胜（5 人局 0.51），分散后回到 0.16–0.24。
- **出手上限按人数放宽**：1v1 仍是 30 手，群架每多一人 +12 手（3 人 42、4 人 54、5 人 66）。不放宽时 5 人局约 16% 没打完就按气血判。
- **深渊领域**：铺开以后，其余每个活人每次真正出手前各吃一口暗流；领域主人自己的攻击次数（`FIELD_TURNS`）照旧扣。
- 这些常数在 B0 用常量起步，B5 由模拟收口。

## 3. 联机协议

### 3.1 组局（星型）

- 房主点「开群架」，局域网广播开桌（复用现有 beacon / neighborhood）；邻居加入，交换名帖（`SparCard`）和 nonce。
- 人数 2–5；**2 人时自动退化成现有 1v1 切磋**，不进混战路径。
- 编号按加入顺序：房主 0，依次 1..N-1。编号在整场不变。
- 所有参与方 `BRAWL_VERSION` 必须一致，否则拒入。

### 3.2 种子与一致性

- 种子 `seedOf([nonce0, nonce1, ...])`，按编号顺序拼接；所有方在开打前都已拿到全部 nonce（先承诺后揭示，同 X5）。
- 引擎、AI、解说随机数全部由种子派生；各家本地重算同一串事件。**网络只传每手的选择，不传事件**。
- 事件一致性不做运行时校验；调试模式下可比较事件序列哈希，发现分歧直接报错。

### 3.3 出手广播

- 轮到编号 i：i 把 `{ index, actor: i, target, action }` 发给房主。
- 房主校验：轮次对、动作在 `legalActions` 里、目标合法、序号连续；通过后转发给其余 N-1 方（含自己）。
- 房主自己出手时直接广播。
- 一方本地定不了（超时 / 没选）→ 用后备挑法（沿用 `fallbackAction` 的口径），仍然广播，不能沉默。
- 每方拿到一手后本地重算，推进自己的演出；**等到自己轮到才发**，不会抢跑。

### 3.4 掉线与退场

- 35 秒没收到某方的这一手（沿用现有 `waitMs`）→ 该方判掉线，广播 `退场`，剩余继续打。
- 认输：本方广播 forfeit，房主确认后转发；全体收到同一个 `forfeit` 结局，不按掉线处理。
- 只剩 1 个活人 / 全员退场 → 结束，各家按同一 `ranking` 结算。

**房主移交**：

- 房主掉线判定：轮到房主出手时其余方 35 秒收不到，或房主作为中继连续失联（转发超时）。
- 接任者 = **剩余存活方里编号最小的一只**。这条规则是确定的，各家本地算出的新工头一致，不需要协商。
- 接任者广播 `hostChange { epoch, host }`，`epoch` 从 0 递增；收到公告即把出手的收件地址换成新房主。**旧 epoch 的报文一律丢弃**，避免新旧房主同时转发造成分歧。
- 原房主本场按掉线处理，**不再重新入场**（局域网里 35 秒无响应基本就是真掉线；卡顿恢复的也不搞特殊，免得状态机分叉）。
- 移交途中又掉一个：按同一规则再交给下一个存活编号；只剩 1 人则结束。

### 3.5 协议载荷

- 沿用现有 HTTP 逐手接口的形状，新增 `brawl` 路由族：开桌、加入、亮 nonce、递交每一手、退场。
- 每手最多 `{ index, target, action }`，动作仍按 `parseSparAction` 的口径校验；目标编号单列，不塞进动作结构。
- 不收结算结果、不收修为、不收收益。

## 4. 演出

### 4.1 环形摆位

- 本机宠物在**正下方（6 点钟）**，其余按编号顺时针等分（3 人 120°、4 人 90°、5 人 72°）。
- **每种人数都要有配套观感**，不是只为 5 人做：2 人退化成现有 1v1；3 / 4 人时窗口按人数放大（人越少每只越大），3 人局尽量接近 1v1 的单只尺寸；5 人才缩到最小档。半径与窗口大小一起按人数算，不留大片空桌面。
- 环心 = 本机宠物窗口中心；半径按工作区自适应：先保证四角窗口不越界，再按当前人数的最小可读窗口反推最大半径。
- 对手窗口复用 `foe-window.ts`，开 N-1 个实例；每只朝向环心（左半环 `facing: 'right'`，右半环 `facing: 'left'`，正上方向下）。
- 开打前锁定摆位；本机宠物被拖动 / 甩动时整环跟随（复用现有跟随与 `/position` 的 `line`）。
- 屏幕放不下时按顺序处理，**不缩人数**：
  1. 先平移整个环，必要时把本机宠物窗口挪到工作区内合适的位置；
  2. 再让所有窗口**等比缩小**（相对大小不变），最小到 120px 仍可读；
  3. 两者都做完了还放不下，才提示房主把系统缩放调小或换更大的屏。

### 4.2 命中落到具体目标

- `Stage` 表从 `[self, foe]` 改成按编号取；`fxBounds` 取所有舞台的联合矩形（现有实现天然支持任意多矩形）。
- 飞行物：`from = bodyPoint(stages[actor])`，`to = bodyPoint(stages[target])`；`arc` / `line` / `ground` 等轨迹按两点连线与夹角算，不再假设「左打右」。
- 冲刺：从 actor 舞台朝 target 舞台中心直线冲，距离按两矩形间距算；退回原位。
- 受击 / 闪避 / 泡泡 / 魂影 / 假死遁：只播在 `target` 那只的窗口上，其余不抖。
- 静帧类（白袍、符纹、门）的 `anchor` 从 `self/foe` 改成 `actor/target/mid`。

### 4.3 血条与信息

- 每只头顶一条名字 + 气血小条（对手窗口页面内嵌，自家沿用现有宠物窗口的挂件）。
- 环心放一块记分板（改 `arena-window.ts`）：按编号列存活状态与剩余气血，标示当前出手者。
- 淘汰：该只播倒地 → 淡出到 30% 透明度 → 血条置灰，留在环上不消失（围成一圈的构图不塌）。
- 解说台词沿用 `battle-lines.ts` 的模板，补「打谁」的措辞；N 人局不逐手念，按事件频率抽样。

### 4.4 时间线

- 新增 `brawlTimeline(events, names: string[])`，输出 `Step` 的扩展版：`who: number`、`target?: number`、`hp: number[]`。
- 同一时刻多人出手已由引擎串行化，演出按事件顺序连播，不并行抢舞台。
- 尽量贴 1v1：单次命中的动作、飞行物、受击、停顿、音效、血条跳动全沿用现有 `ATTACK_SHOW` / `FxTrack` 的口径，只换坐标与编号。

## 8. 风险

- **演出窗口数量**：5 个 Electron 窗口同屏，帧率和层级要真机验；必要时把 4 个对手窗口合并进一个全景擂台窗口（B1 先按多窗口做，卡了再换）。
- **确定性重算**：任何一处随机数抽取顺序不一致都会导致联机分歧；B0 就把「选目标固定抽一次」钉死，B3 加哈希校验兜底。
- **平衡**：5 人局被集火的一方几乎必死，先手和仇恨策略要单独调；不能直接套 1v1 的 65% / 30% 就完事。
- **规则重复**：新内核与旧内核共享常量但不共享实现，后续改一条规则要改两处；用公共辅助函数收敛，别让两边漂移。
